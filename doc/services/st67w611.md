# st67w611: STMicroelectronics ST67W611M1 Wi-Fi/BLE combo module driver

The `st67w611` service drives the ST67W611M1 Wi-Fi/BLE module connected over SPI. The module runs ST's NCP (network
co-processor) AT firmware, the driver talks to it using AT commands framed over SPI and exposes the Ble, Wifi, Tcp,
Tls and Clock (SNTP time) interfaces. The module runs the t01 firmware variant, which has the TCP/UDP/HTTP stack
built in, the TCP/IP stack is not run on the MCU.

The AT command reference the driver is written against (version 2.0.106) is kept next to the driver source in
`services/st67w611/at-commands-2.0.106.html`.


## Wi-Fi/BLE coexistence

Wi-Fi and BLE share a single radio in the module. Without coexistence enabled, heavy Wi-Fi traffic (eg. a firmware
download) competes with an active BLE connection, the transfer stalls and the station is eventually disconnected
from the AP.

The driver enables the coexistence about 2 s after every station connection got its IP address (the module is busy
right after that) using `AT+CWCOEXDUTY` followed by `AT+CWCOEXEN=1`. It is tried once per connection, a failure is
logged as a warning. Wi-Fi gets `ST67W611_COEX_WIFI_MS` (70 ms) of each 102.4 ms TBTT period, BLE the rest.

!!! note
    Both commands are documented for the AT firmware 2.0.106. The module firmware currently used (AT version
    1.0.0.1, SDK 2.0.89) answers both with `ERROR`, the coexistence is not enabled until the module firmware is
    updated. The documentation is not consistent about the order of the two commands, it may have to be swapped
    once tested with a firmware supporting them.


## Future work


### Module firmware update (OTA)

The module firmware has to be updated from the MCU, eg. to get the Wi-Fi/BLE coexistence support. This is not
a priority now.

The firmware images are provided by ST in the X-CUBE-ST67W61 package, in
[Projects/ST67W6X_Scripts/Binaries/NCP_Binaries](https://github.com/STMicroelectronics/x-cube-st67w61/tree/main/Projects/ST67W6X_Scripts/Binaries/NCP_Binaries).
The t01 images (TCP/UDP/HTTP stack in the module) are used. Images are either uncompressed or xz compressed, about
800 KB compressed.

The update is done using the module's AT OTA commands over the existing SPI link:

1. `AT+OTASTART=1` starts the OTA transmission (`AT+OTASTART=0` aborts it).
2. `AT+OTASEND=<length>` sends a chunk of the image. The module answers with the `>` prompt, the data is sent after
   it and the module answers `SEND OK` or `SEND FAIL`. A chunk is at most 4096 bytes, the first one must be longer
   than 512 bytes. The data is written to the inactive `FW` partition in the module and verified on the fly.
3. `AT+OTAFIN` verifies the image and reboots the module from the other partition.

`AT+PART?` reports the active `FW` partition index and its age (incremented with every OTA update), it can be used
to check that the update succeeded.

The `>` prompt exchange is the same as the one already used for `AT+BLEGATTSNTFY` (`st67w611_command_data()`).

Work needed:

- **Flash partition for the image.** The image is stored in the external flash before it is sent to the module.
  A new static flash volume is needed, at least 1 MiB to hold an xz compressed image. On nwdaq-main-hh1 the
  `flash1` partitions currently end at `0x280000`.
- **Getting the image there.** Eg. the updater applet downloading the module image to the partition, the same way it
  downloads the MCU firmware to `fw-update`.
- **Driver support.** OTA start/send/finish in the driver, reading the image from a Flash interface given to it,
  decompressing xz images on the fly (`lib/xz-embedded`, already used by `flash-updater`) and sending them in
  4096 byte chunks. The module reboots after `AT+OTAFIN`, the driver has to go through its boot/init sequence again
  and re-apply the Wi-Fi and BLE configuration.
- **Version check.** The module firmware version is read using `AT+GMR` at init (and printed to the log), it can
  be used to decide whether the update is needed.
